### ❓ Вопрос 1
**Какой параметр отвечает за то, насколько быстро CB откроется при постоянных ошибках (полный даунтайм сервиса)?**

Параметр threshold_consecutive регулирует сколько ошибок подряд должно возникнуть перед открытием цепи



### ❓ Вопрос 2
**Какой параметр позволяет CB открываться при редких ошибках (`rare_error`)?**

Параметр threshold_percentage регулирует какой процент ошибок в рамках заданного временного окна (interval) должен быть достигнут для открытия цепи.
Если установить threshold_percentage <= 5%, то CB рано или поздно откроется (т.к в режиме rare_error ошибка выпадает с 5% шансом)



### ❓ Вопрос 3
**Какой параметр отвечает за время нахождения в OPEN и полную блокировку трафика?**

Параметр timeout регулирует время нахождения в OPEN перед перемещением в HALF-OPEN.



### ❓ Вопрос 4
**Какой параметр отвечает за поведение в HALF-OPEN?**

В реализации gobreaker (https://github.com/sony/gobreaker) можно найти такой сниппет:

```go
func (cb *CircuitBreaker[T]) onSuccess(state State, age uint64, now time.Time) {
    switch state {
        case StateClosed:
            cb.counts.onSuccess(age)
        case StateHalfOpen:
            cb.counts.onSuccess(age)
            if cb.counts.ConsecutiveSuccesses >= cb.maxRequests {
                cb.setState(StateClosed, now)
            }
        }
}
```

Параметр max_requests задает количество "пробных" запросов в статусе HALF-OPEN. 

Если все запросы завершатся успешно, то цепь замкнется (конечный автомат перейдет в статус CLOSED).

Если же хотя бы один запрос из max_requests провалится, то будет осуществлен переход в статус OPEN.



### ❓ Вопрос 5
**Какие параметры влияют на скорость восстановления при `slow → ok`?**

Напрямую влияет параметр timeout, регулирующий время перед переходом OPEN -> HALF OPEN.

Также при высокой нагрузке может влиять параметр max_requests. Он регулирует количество пробных запросов в состоянии HALF OPEN.

В состоянии ok все запросы заканчиваются успехом, поэтому переход из HALF OPEN в CLOSED гарантирован через max_requests запросов.
Однако пока не будут зафиксированы успехи этих запросов, запросы, отправленные позже первых max_requests запросов после перехода в HALF OPEN будут отброшены с ошибкой 429. 



### ❓ Вопрос 6
**Какие сайд-эффекты можно получить, установив timeout слишком маленьким/большим?**

При очень маленьком timeout переходы OPEN -> HALF OPEN могут быть слишком частыми, как следствие, трафик в страдающий сервис продолжится и может мешать его восстановлению.

При очень большом timeout мы рискуем получить излишнюю деградацию нашего сервиса, поскольку не будем разрешать трафик в сторонний сервис слишком долго, хотя он уже мог восстановиться.


### ❓ Вопрос 7
**Почему я пришел к выводу, что надо создавать для каждой ручки (или связки сервис + ручка) отдельный CB? Почему я не сделал единый CB для всего сервиса `analytic`?**

Каждая ручка имеет свою логику, свое ожидаемое поведение (ошибки, таймауты), поэтому корректно разделять CB для отдельной конфигурации каждой ручки на основе именно ее статистики
