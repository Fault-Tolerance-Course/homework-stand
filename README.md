Тимлид поручает Игорю разобраться.

Перед тем как разбираться с probes и graceful shutdown, важно понимать,
**как именно Docker Compose определяет состояние контейнера**  
и почему иногда «всё сломалось», хотя контейнер всё ещё работает.

Ниже — разбор `healthcheck` и роли `autoheal`.

---

## 🩺 Как работает `healthcheck` в Docker Compose

По умолчанию каждый контейнер после запуска находится в статусе: `starting`


Далее в работу вступает секция `healthcheck`.
---

### 🎯 Что делает `healthcheck`

`healthcheck` решает **одну простую задачу**:

- опросить контейнер на предмет *живости*
- если контейнер жив → статус становится `healthy`
- если контейнер не жив → статус становится `unhealthy`

И всё.  
`healthcheck` **не управляет трафиком, не рестартит контейнер и не чинит ошибки**.

> Healthcheck постоянно прашивает контейнер, точно так же, как и оркестратор, который постоянно опрашивает наш контейнер в production.
---

## 🔁 Как происходит проверка на живость

### ⏳ `start_period: 10s`

- healthcheck **начинает выполняться сразу**
- но **неудачные попытки не учитываются** в течение первых `10 секунд`
- это «поблажка» контейнеру, чтобы он успел запуститься

---

### 🔄 `retries: 5`

- количество **подряд идущих неудачных попыток**
- после которых контейнер считается `unhealthy`

---

### ⏱ `timeout: 4s`

- максимальное время ожидания **одной** попытки
- если команда не уложилась — попытка считается неуспешной

---

### ⏲ `interval: 5s`

- время **между попытками** выполнения healthcheck

---

### 🧪 `test`

- команда, которая выполняется **внутри контейнера**
- Docker смотрит **только на exit code**

| Exit code | Результат |
|---|---|
| `0` | попытка успешна |
| `!= 0` | попытка неуспешна |

stdout / stderr **не анализируются**.

---

> В нашем случае: у healthcheck'а есть 10 + 5*5 = 35s на выполнение проверок. 
Этого хватет для того, чтобы файлик был загружен.


## 🚨 Важный момент: `unhealthy` — это тупик

Если контейнер перешёл в статус: `unhealthy`


то:

- Docker Compose **не перезапустит его автоматически**
- контейнер продолжает работать, но помечен как нездоровый
- сам по себе он **не вернётся в `healthy`**

---

## 🔧 Для этого нужен `autoheal`

### 🧩 Что делает `autoheal`

`autoheal` — это отдельный контейнер-наблюдатель, который:

- следит за контейнерами с лейблом:

```yaml
labels:
  - autoheal=true
```

- если контейнер с этим лейблом перешёл в unhealthy
- перезапускает его

## Как посмотреть, что происходит с контейнером

### 1. `docker ps`

Команда `docker ps` показывает сводную информацию по всем запущенным контейнерам:

- список контейнеров
- текущий статус контейнера (`starting`, `healthy`, `unhealthy`)
- время работы (uptime)
- идентификатор контейнера

Эта команда удобна для быстрого обзора состояния системы.

---

### 2. `docker inspect <container_id>`

Команда `docker inspect` позволяет получить подробную информацию о конкретном контейнере.

С её помощью можно увидеть детали, связанные с `healthcheck`:

- текущий health-статус контейнера
- количество подряд неуспешных проверок
- значение `failstreak`
- историю выполнений healthcheck-команд

Команда особенно полезна для отладки проблем со стартом контейнера и некорректной работой `healthcheck`.

## Поведение контейнера при `cordon / uncordon` в Docker Compose

В Docker Compose нет управления трафиком, как в Kubernetes.

Поэтому в рамках данного задания `cordon / uncordon` реализуется **на уровне приложения**
через изменение поведения `healthcheck`.

---

## Что означает `cordon`

При переводе контейнера в состояние **cordon** приложение должно:

- ❌ перестать считаться *здоровым*
- ❌ сигнализировать внешней системе, что контейнер **не готов принимать новые запросы**
- ✅ продолжать работать и обрабатывать уже начатые операции
- ✅ оставаться запущенным и доступным для отладки

Технически это реализуется так:

- `healthcheck` начинает **возвращать ошибку** (`exit code != 0`)
- контейнер переходит в статус `unhealthy` ТОЛЬКО ПО ДОСТИЖЕНИЮ КОЛИЧЕСТА RETRY'ев, которое мы указали в compose файле
- Docker Compose помечает контейнер как нездоровый

---

## Что означает `uncordon`

При переходе в состояние **uncordon** приложение должно:

- снова успешно проходить `healthcheck`
- вернуть `exit code = 0`
- перейти в статус `healthy`

Контейнер **не перезапускается**, состояние меняется динамически.

Тут можно поставить побольше попыток, чтобы мы отловили контейнер в статусе starting и могли его перевести в `uncordon`.

---

## Важное ограничение Docker Compose

В отличие от Kubernetes:

- Docker Compose **не исключает контейнер из балансировки автоматически**
- Docker Compose **не управляет трафиком**
- статус `unhealthy` — это **информационный сигнал**

Поэтому:
- реальный контроль трафика происходит **в приложении или на клиенте**
- healthcheck используется как **индикатор состояния**, а не как маршрутизатор

---
