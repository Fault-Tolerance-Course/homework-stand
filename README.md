# 🧩 Кейс: «Категории, которые исчезали»

## 🎭 Контекст истории

Компания **«ХвостСервис»** выкатывает новый релиз. Один из микросервисов — `task-service`, который отдаёт категории задач для фронтенда.

Разработчик **Игорь** добавил загрузку справочника категорий из файла при старте сервиса. Загрузка занимает ~30 секунд.

После загрузки сервис отвечает корректно.

Однако в момент деплоя фронтенд иногда начинает получать **пустой список категорий**. Через ~30 секунд данные появляются сами, но к этому моменту уже:

- пользователи пугаются,
- аналитики говорят «категорий нет»,
- менеджеры задают вопросы.

Тимлид поручает Игорю разобраться.

---

## Наблюдения

- Деплой выполняется через **rolling update** (почитать, что это такое) с 2 репликами.
- На старте сервис поднимает HTTP-сервер и загружает файл с категориями.
- Пользватели в течении 30 секунд видят пустоту на экране
- На стенде видно, что новый Pod **иногда получает трафик до загрузки файла**.
- В коде есть флаг `termination` (назначение неочевидно).
- Нет возможности вывести под из балансировки вручную без перезапуска, поэтому отладка вызывает боль

---

## Требования тимлида

> «Нужно найти место загрузки файла. Pod не должен считаться готовым, пока не загрузил данные, и не должен отдавать пустые категории на старте»

> «Реализовать механизм, который позволит сказать окрестратору, что pod временно не будет обслуживать трафик. Взгляни на механику cordon/uncoedon в кубе.
> Вот референс https://cast.ai/blog/kubernetes-cordon-how-it-works-and-when-to-use-it.
> Это нужно нам для исследований и раскопок во время проблем, пригодится»

### Задача 1 — Пока справочник категорий не загружен → Pod **не готов**.

Выбрать нужный тип пробы и реализовать в ней логику, позволяющую понять оркестатору, что севрис _task-service_ в боевой готовности и категории успешно загружены

Убедиться в наличии проблемы можно лично запустив стенд и дернув ручку получения категорий `/v1/categories`

**Ожидание:** новый Pod не участвует в балансировке раньше времени.

## Технические ожидания

После выполнения решения:

1. Контейнеры `task-service` считаются ready только после загрузки файла с категориями

- контейнер перейдет из статуса `unhealthy` -> `healthy` ~ через 30сек (после загрузки файла)
- не будет перезапущен
- введя команду `docker ps` после первой итерации _health check_ статус контейнера будет unhealthy, а через 30 сек он сменится на `healthy`
- так же `autoheal` будет видеть контейнер в промежуточном состоянии и не будет перезапускать его

2. Появилась возможность вручную (или же автоматикой) выводить контейнеры из балансировки

- вызовы ручек `/cordon` + `/uncordon` переключают состояние контейнера (healthy / unhealthy)
- введя команду `docker ps` после переключения и наступления итерации _health check_ статус контейнера будет меняться (будет перезапущен)

## Критерии успеха

- **Функционально**: пользователи не видят пустых категорий
- **Операционно**: есть механизм «поднять → прогреть → включить в трафик»
- **Инженерно**: понятна роль `termination` и lifecycle сигналов
- **Kubernetes-логически**: готовность Pod отражает фактическую готовность
